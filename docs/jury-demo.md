# Сценарий демонстрации

Команда `repairflow demo` разворачивает воспроизводимый лабораторный стенд на синтетическом ремонтном участке. Это не выгрузка СВАРЗ. Числа по памяти не зачитываются: открывается файл, который записала команда, или таблица в [`../README.md`](../README.md), которую собирает `tools/attest.py`. Задачу «решил интеллект» не говорят.

## Пошаговый разбор прогона `repairflow demo --out out`

1. **Исходная задача.** В файл `out/repair-site-mvp.json` записывается сгенерированный экземпляр ремонтного участка: заказы со сходящимися технологическими картами, рабочие посты с матрицей переналадки, бригады с допусками, оснастка, сменные календари, запчасти, обменный фонд и замороженные слоты.
2. **Наивная база FIFO (`out/fifo.json`).** Диспетчеризация в порядке очереди без учёта всех сопряжённых ограничений приводит к конфликтам на постах и в бригадах. Независимый нотариус отклоняет этот график с ненулевым кодом выхода и полным списком причин.
3. **Жадный планировщик GREED (`out/greed.json`).** Построенное расписание проходит проверку независимого нотариуса без жёстких нарушений и получает статус `verified` (`verified_feasible=true`, код выхода `0`). Рядом формируются текстовая сводка `out/greed.md` и автономная диаграмма Ганта `out/greed.html`.
4. **Точный решатель CP-SAT (`out/cpsat.json`).** Если не передан флаг `--skip-cpsat`, на компактном примере запускается ограниченный по времени CP-SAT. Прогон называют точным только тогда, когда в этом файле так и написано: статус `optimal` стоит лишь при доказанном `OPTIMAL` за один проход компилятора и пустом нотариусе.
5. **Перепланирование после сбоя (`out/post-down.json`, `out/replan.json`, `out/replan-diff.json`).** Сценарий моделирует внеплановую остановку поста на интервале последнего визита: прежний план при перепроверке закономерно отклоняется с кодом `CALENDAR_BROKEN`, а пересчитанный график восстанавливает допустимость (`replan_verified=True`) и сохраняет все незатронутые замороженные назначения (`frozen_moved=0`).
6. **Перехват намеренно испорченного плана (`out/broken.json`).** В допустимый график вносится искажение и передаётся нотариусу. Строка готовности требует код выхода `2`. Зачитывать нужно файл и эту строку.
7. **Проверка внешнего цехового листа (`out/shop-plan.csv`, `out/shop-verify.json`, `out/shop-reasons.txt`).** Таблица CSV, в которой одна операция поставлена на несуществующий пост, проверяется доменным контуром `verify-plan` без вызова ядра (`claim=rejected`, `verified_feasible=false`), а в текстовом отчёте указывается имя файла и номер строки с ошибкой. Набор контрольных примеров для пяти видов цеховых ошибок находится в каталоге `schemas/templates/five-errors`.
8. **Объяснение отказа (`out/witness.json`).** Для испорченного плана выделяется минимальный по удалению набор идентификаторов операций, воспроизводящий доменный код нарушения (это локальный свидетель конфликта операций, а не CP-MUS/MCS).
9. **Журнал решений оператора (`out/decisions.jsonl`).** Принятие проверенного плана `greed.json` записывается в журнал с хеш-цепочкой версии `v2` и сразу проверяется на целостность. Та же проверка отдельно — `repairflow log verify out/decisions.jsonl`. Демо ключ свидетеля не пишет: для `repairflow log witness` нужен файл ключа вне репозитория.

При успешном завершении всех девяти шагов в консоль выводится итоговая строка `MVP readiness: PASS`.

## Сборка папки подачи

Кампания намеренной порчи планов (`docs/fault-campaign.json`) и кампания цеховых сбоев (`docs/disruption-campaign.json`) хранятся в репозитории отдельно, а числовая выжимка из них и манифеста доказательств автоматически собирается в [`submission-facts.md`](submission-facts.md).

Команда:

```bash
python tools/pack_submission.py --out out/submission
```

копирует главную страницу, карточку заявки, этот сценарий показа, матрицу прослеживаемости, ответы на вопросы, список границ, сводку показателей, манифест доказательств и отчёт кампании порчи в каталог `out/submission/` и фиксирует SHA-256 каждого файла в `PACKET.json`.
