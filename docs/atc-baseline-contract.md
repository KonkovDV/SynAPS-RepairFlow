# Локальный договор упорядочения ATC

## Назначение модуля

Модуль `src/repairflow/atc_baseline.py` задаёт детерминированный порядок готового списка операций в духе Apparent Tardiness Cost. Это база для сравнения. Она нарочно отделена от API ядра SynAPS и от планировщика.

`repairflow.planner` функцию `atc_order` не вызывает. Режим `--preset ATC` и `repairflow benchmark --solvers ATC` ранжируют операции собственным списочным индексом `_atc_index`. Встройка `atc_order` в планировщик — отдельная правка. Граница независимого нотариуса при ней не ослабляется.

Модуль не строит расписание и не выдаёт вердикт `verified`.

## Формула модуля `atc_baseline`

Для операции `i` из списка, который передал вызывающий, в явно заданный момент `now`:

```text
slack_i = max(d_i - now - p_i, 0)
ATC_i   = (w_i / p_i) * exp(-slack_i / (k * p_bar))
```

- `w_i` — `max(1, Job.priority)`: большее число срочнее, как в правиле `EDD`;
- `p_i` — `Operation.duration_min` в минутах;
- `d_i` — `Job.due_date`, а если срок не задан — конец горизонта `planning_horizon.end`;
- `now` — аргумент вызывающего, не системные часы;
- `p_bar` — средняя длительность операций в переданном списке;
- `k` — конечное число строго больше нуля; в `ATCConfig` по умолчанию `2.0`.

При равном весе порядок такой: больший вес, более ранний срок, более короткая операция, затем идентификатор по возрастанию. В коде это кортеж `(-score, due_date, duration_min, operation_id)`.

## Чего модуль не делает

- не решает, какие операции уже готовы по предшественникам;
- не назначает посты, бригады, оснастку и полосы;
- не считает переналадку, календари, запчасти и пересчёт после сбоя;
- не вызывает ядро SynAPS и не подменяет нотариус;
- не объявляет план `optimal`.

Повтор идентификатора и неизвестная операция отвергаются. Неположительное или бесконечное `k` и неположительная средняя длительность тоже отвергаются.

## Списочное правило планировщика, это другой расчёт

Индекс в `planner._atc_index` считается только среди операций, которые списочный планировщик уже считает готовыми:

```text
now      = max(начало горизонта, release заказа, earliest_start,
               концы уже поставленных предшественников)
duration = max(duration_min, 1)
slack    = max(due - now - duration, 0)
mean     = max(средняя длительность готового набора, 1)
ATC      = (Job.priority / duration) * exp(-slack / (2.0 * mean))
```

Вес здесь — само поле `Job.priority`, без подъёма до единицы. При равном индексе раньше берётся меньший `operation_id`. В метаданные плана пишутся `dispatch_rule = repairflow_atc` и `atc_k = 2.0`.

Чистый план этого правила может получить `claim_status = verified` и статус решателя `HEURISTIC_FEASIBLE`. Статус `optimal` ему не присваивается.

## Что записывать в замер, если сравнивается планировщик

В строке замера с решателем `ATC` остаются зерно, `input_hash`, `config_hash`, `schedule_hash`, `result_hash`, коммит SynAPS, вердикт нотариуса и те же показатели от начала горизонта, что у `FIFO`, `EDD`, `GREED` и `CPSAT`: `makespan_minutes`, `total_tardiness_minutes`, `total_setup_minutes`, `coverage`. Сам модуль `atc_baseline` такой строки не создаёт.
