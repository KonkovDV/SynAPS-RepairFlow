# Состав поставки,SBOM и криптографические отпечатки

## 1. Опись прямых компонентов (CycloneDX SBOM)

Функция `repairflow.sbom.build_sbom` (и скрипт `python tools/write_sbom.py`) формирует документ в формате **CycloneDX 1.5** по четырём прямым пакетам среды выполнения: `synaps-repairflow`, `synaps`, `pydantic` и `ortools` (версия `ortools` жёстко зафиксирована на `9.15.6755`).

Помимо стандартной карточки CycloneDX, в документ включается блок `runtime_binding` (`repairflow.runtime_binding.v1`). Для каждого прямого пакета в нём перечисляются установленная версия, список всех реально существующих на диске файлов дистрибутива с индивидуальными SHA-256 дайджестами и итоговый сводный хеш `manifest_sha256`, вычисленный по отсортированным парам `(относительный_путь, sha256)`. Это позволяет без обращения к сети и внешним индексам пакетов проверить, что файлы в установленном окружении не изменялись. Отсутствующие пакеты явно помечаются статусом `absent`, а пакеты без читаемых файлов — статусом `empty`.

## 2. Замок архивов и паспорт артефакта

Поверх описи установленных файлов работают ещё две структуры контроля поставки:

- **`repairflow.dependency_lock.v1`** — проверяет наличие архивов колёс или исходников для прямых компонентов. Статус `locked` присваивается только тогда, когда у каждого компонента архив присутствует (`present`) и снабжён дайджестом SHA-256; в противном случае (например, при редактируемой установке `pip install -e .`) выставляется статус `incomplete`.
- **`repairflow.artifact_record.v1`** — фиксирует SHA-256 локального колеса или `sdist`-архива и считывает хеш PEP 610 из `direct_url.json`, если пакет ставился по прямому URL. Для редактируемой установки фиксируется `editable`, для алгоритмов хеширования кроме SHA-256 — `unsupported_hash`. Поле `closure_status` имеет значение `installed_environment_not_a_lock` и явно ссылается на `repairflow.runtime_binding.v1`, а полная заморозка всех транзитивных колёс с дайджестами SHA-256 хранится отдельно в файле `requirements-lock.txt` (`tools/verify_lock.py`, `tests/test_lock_hashes.py`).

Поскольку закрытый ключ подписи релизов в репозитории не хранится, все поля криптографической подписи в этих записях имеют явный статус `absent`.

## 3. Отпечатки задачи, расписания и результата

Каждый файл результата (`repairflow.result.v1`) содержит четыре связанных SHA-256 отпечатка:

| Поле | Что входит в расчёт хеша | Зависимость от платформы |
| --- | --- | --- |
| `input_hash` | Каноническое JSON-представление входной задачи `RepairFlowProblem`. | Не зависит от ОС и машины. |
| `config_hash` | Имя решателя, параметры компилятора и паспорт среды выполнения (`runtime_manifest`: версия Python, платформа, версия RepairFlow, коммит SynAPS, версии OR-Tools и Pydantic). | Зависит от машины и окружения. |
| `schedule_hash` | `input_hash`, имя решателя, коммит SynAPS, канонически отсортированные назначения, `claim_status`, `exit_code` и отсортированные коды нарушений (без текстовых сообщений и без `runtime_manifest`). | **Совпадает между Windows и Linux** на одном и том же расписании. |
| `result_hash` | Полный отчёт результата, запечатанный поверх `schedule_hash` и включающий `config_hash` и паспорт среды выполнения. | Привязывает конкретный файл отчёта к машине, на которой он был собран. |

Команда `repairflow check PROBLEM RESULT --verify-hashes` пересчитывает эти отпечатки (и отвергает пустой `schedule_hash`) до запуска проверок нотариуса: при любом несовпадении возвращается код выхода `1`.
